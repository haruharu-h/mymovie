# k6

バックエンド（Fastify）に対する負荷試験・性能検証スクリプト集。

## k6とは、なぜ使うか

[k6](https://k6.io/)はGoで書かれた負荷試験ツール。テストシナリオ自体はJavaScriptで書く（Node.jsではなくk6独自のJSランタイムで動く。`fetch`ではなく`k6/http`モジュールを使うのはそのため）。

このディレクトリのスクリプトは大きく3つの目的で使い分けている。

- 「デプロイ前に大崩れしていないか」の**サニティチェック**（health-load-test.js, authenticated-flow.js）
- 「同時アクセスでデータが壊れないか」という**DB整合性の検証**（db-pool-stress.js, duplicate-review-race.js）
- 「どこまでVU（仮想ユーザー）数を上げたら性能が落ちるか」を探る**キャパシティ限界の探索**（browsing-ceiling.js, write-ceiling.js）
- 「ビジネスイベントの計装が実際に届いているか」の**可観測性の検証**（span-attribute-verification.js）

`k6/`にはpackage.jsonも設定ファイルも無い。各スクリプトは外部依存のない単一ファイルで、k6本体（Docker、またはローカルインストールしたk6コマンド）に直接渡して実行する。npm installは不要。

## 実行方法

### Dockerで動かす（推奨）

各スクリプトの`BASE_URL`のデフォルト値が`http://backend:3000`になっている。これは`docker-compose.yml`のbackendサービス名を指しており、k6コンテナをbackendと同じDockerネットワークに参加させて実行する前提になっている。

```bash
# 1. backend（とDB等の依存サービス）を起動しておく
docker compose up -d backend

# 2. 参加させるネットワーク名を確認する（compose projectのディレクトリ名から自動生成される。
#    例: リポジトリを"MymovieProject"としてcloneした場合は mymovieproject_default）
docker compose config | grep -A2 "^networks:"

# 3. スクリプトを標準入力経由でk6コンテナに渡す（スクリプトが他ファイルをimportしないため、
#    ボリュームマウント不要でこの形で完結する）
docker run --rm -i --network mymovieproject_default grafana/k6 run - < k6/health-load-test.js
```

ネットワーク名が想定と違う場合は`docker network ls`で実際の名前を確認する。

### ローカルにk6をインストールして動かす

```bash
brew install k6

# backendはdocker-compose.ymlでホストの3000番に公開されているため、localhostで届く
k6 run k6/health-load-test.js -e BASE_URL=http://localhost:3000
```

### 本番（Cloud Run）に向けて実行する

`BASE_URL`を`-e`で上書きするだけで同じスクリプトを使い回せる（各スクリプトが`__ENV.BASE_URL || 'http://backend:3000'`という形でフォールバックを持っているのはこのため）。この場合Dockerネットワークへの参加は不要（インターネット経由で到達するため）。

```bash
docker run --rm -i grafana/k6 run -e BASE_URL=https://<cloud-run-url> - < k6/write-ceiling.js
```

## スクリプト一覧

### サニティチェック（性能目標ではなく「動くか」の確認）

**health-load-test.js** — 10 VU・30秒、`GET /health`を1秒間隔で叩くだけの最小構成。認証もcheckもthresholdも無い。最初に「そもそもコンテナが負荷に耐えて生きているか」を見る、一番手前に置くテスト。

**authenticated-flow.js** — 5 VU・20秒。ログイン→検索→レビュー投稿という実際のユーザー操作に近い一連の流れを通す。`setup()`でテストユーザーと映画を1組だけ事前に用意し、負荷本体では毎回ログインし直す（本物のセッションに近い状態を作りつつ、TMDBへの問い合わせは検索以外で発生させない）。しきい値はエラー率5%未満・p95が3秒未満という緩い基準で、性能目標ではなく「大崩れしていないか」のチェック。レビュー投稿には`http.expectedStatuses(201, 409)`を渡す`responseCallback`を使っており、同じユーザーが同じ映画に2回目以降レビューする409（業務ルール上の正常系）をk6の失敗判定に含めないようにしている（k6の`http_req_failed`メトリクスはデフォルトで200〜399しか成功扱いしないため、これを指定しないとthresholds判定がズレる）。

### DB同時実行・データ整合性の検証（スループットではなく「壊れないか」を見る）

**db-pool-stress.js** — 20 VU（DBクライアントのデフォルト接続プール上限10を意図的に超える人数）を`per-vu-iterations`executorで一斉に1回ずつ発火させる「瞬間的な集中」を作るテスト。`setup()`でVUの数だけ別ユーザーを事前登録し、全員が同じ映画に別ユーザーとしてレビューを投げる設計にすることで、ユニーク制約に引っかからず全リクエストが新規INSERTになる。これによって「重複を弾く挙動」を混ぜずに、コネクションプールが尽きたときに順番待ちになるだけでエラー落ちしないかを純粋に検証できる。しきい値はエラー率1%未満のみで、レイテンシは問わない（プール待ちで遅くなること自体は許容範囲）。

**duplicate-review-race.js** — 10 VUを`per-vu-iterations`executorで一斉に発火させるが、今度は全VUが**同じユーザー・同じ映画**に同時にレビューを投げる。k6のカスタムメトリクス（`Counter`）で201件数・409件数をそれぞれ数え、しきい値`review_created_201: ['count==1']`で「同時アクセスでもDBのユニーク制約により成功は必ずちょうど1件になる」ことを検証する。これは性能試験ではなく、競合状態下でのデータ整合性そのものを確認するテスト。

### キャパシティ限界の探索（本番相当環境でどこまで耐えるか）

**browsing-ceiling.js** — `ramping-vus`executorで10VU→1200VUまで10段階（各30秒、合計5分）にランプアップする。対象は映画詳細取得・レビュー一覧・自分のプロフィール・ユーザー検索・フォロー一覧など、すべてDBのみに触れTMDBを一切呼ばない読み取り系エンドポイント。`setup()`で3ユーザー分・計60本の映画とレビューを事前に用意し、アクセストークンもVUごとに一度だけ取得して使い回す（毎回ログインし直すとargon2idのパスワードハッシュ比較コストが乗ってしまい、見たい「読み取り経路の限界」がぼやけるため）。しきい値は`scenario:browsing`タグに絞ってエラー率5%を超えたら自動停止（`abortOnFail`。無駄に負荷をかけ続けない）。DBコネクションプール枯渇はエラーではなく待ち時間の増加として現れるため、エラー率だけでなくp95レイテンシ（2秒未満）も別途見ている。

**write-ceiling.js** — browsing-ceiling.jsと同じ10VU→1200VUのランプ形状だが、こちらは毎イテレーションで新規ユーザー登録→ログイン→レビュー投稿というフルの書き込み経路を通す。イテレーションのたびに本物のargon2ハッシュ計算と新規INSERTが発生するため、読み取り側とは別に「書き込み経路の限界」を探れる。メールアドレスの一意性は`RUN_ID`（モジュール読み込み時に決まる乱数）と`__VU`・`__ITER`の組み合わせで担保し、再実行時の衝突を避けている。しきい値はエラー率5%超で自動停止する点はbrowsing-ceiling.jsと同じだが、`delayAbortEval: '60s'`で判定開始を60秒遅らせている。これは開始直後のコールドスタート起因の一時的なエラーで、サンプル数が少ないうちに誤って早期停止しないようにするための調整。

### 可観測性の検証

**span-attribute-verification.js** — 2 VU・10イテレーションという低負荷（`per-vu-iterations`）で、ビジネスイベントのログ・span属性（映画登録結果・レビュー作成結果）が実際にトレーシングバックエンドまで届くかを目視確認するためのスクリプト。限界を探る他のテストとは目的が違うため意図的に低VUに抑えており、パスワードハッシュ計算も`setup()`の1回だけに限定している（高VUで実行すると、ハッシュ計算がスレッドプールを占有し無関係なリクエストを巻き込んでしまうことがあるため）。8種類の映画IDを順番に使うことで、1周目は「新規登録・新規作成」、2周目以降は「登録済み・重複」という異なるビジネスイベントの状態を意図的に両方発生させている。しきい値はエラー率100%未満とほぼ無いに等しく、これはpass/failのゲートではなく目視確認用の補助である。
